[2026-11-12] A connection can withdraw a pending operation it staged itself, without pending_operations:approve (gnubok_withdraw_pending_operation and POST /pending-operations/{id}/withdraw): a staging key had no way to take back a duplicate or a wrong proposal, so it stayed in the person's queue next to the corrected one and the wrong one got approved (crm#1725, crm#1817). The gate is ownership, not a scope: the row's actor_id must be the calling API key or OAuth connection and its user_id the key's user, so it never reaches another agent's or a person's proposal; no single scope fits (each key staged under its own write scope) and a new scope would reach no existing connection, since scopes cannot be added to one. No new status and no migration: the row closes through the one reject write (compare-and-set on status pending, so an operation being committed is left alone) as rejected with rejection_category superseded, the system's value that is never counted as a person's verdict, plus result_data.withdrawn, a rejection_reason that says the stager withdrew it, and a PendingOperationRejected history row marked withdrawn naming the key. The MCP tool is search-only because tools/list is frozen and full, and the stage bridge carries it as its one non-staging target (ridesStageBridge): otherwise no client that only knows tools/list could reach it, and it stays inside the bridge's promise that nothing reaches the books through it. Approve and reject are still never carried. Known difference between the doors: the v1 wrapper refuses every POST from a read-only member, the MCP tool has no scope for the role gate to classify and lets a since-downgraded member's key withdraw its own proposal. Rejected alternatives: letting gnubok_reject_pending_operation act on own proposals without the approve scope (it would change what the Godkänn permission means at the dispatcher), and a new terminal status 'withdrawn' (every reader of status would need it, for no fact the row does not already carry).
