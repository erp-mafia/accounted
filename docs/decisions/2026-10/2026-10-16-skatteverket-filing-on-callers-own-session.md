[2026-10-16] Skatteverket filing (momsdeklaration kontrollera, utkast and lås; AGI) stays on the caller's own BankID session, and every agent surface now reports that per caller instead of validate/submit borrowing another member's session (crm#1263). Why: the token row is per (user, company) by design (token-store.ts: the OAuth token is the person's BankID session), Skatteverket checks the logged-in person's own behörighet for the organisation on each call (api-client.ts maps its 403 "Behörighet" to BEHORIGHET_SAKNAS), and the 2026-08-18 decision (#1673) put only reads on any member's token. Lending member A's session to member B's agent for /kontrollera would make A the actor of B's call at Skatteverket and only move the refusal to approval time, because the commit runs utkast and lås on the approver's own token; the web app's own validate route already runs on the caller's session. So gnubok_get_agent_briefing's skatteverket_connection gains `filing` (ready, own_session, and a message naming the member whose session serves the company's reads), gnubok_connect_skatteverket returns `can_file` and keeps its connect link and card button when the company is connected but the caller is not, and gnubok_vat_declaration_validate/_submit answer SKATTEVERKET_NOT_CONNECTED with that same message and a gnubok_connect_skatteverket remediation. Rejected: the triage proposal to run /kontrollera on the company-wide read lookup (resolveReadAuth), for the reasons above. The swedish-* skills do not cover who may sign a skattedeklaration, so this rests on the existing product decision and Skatteverket's own per-person check, not on a new legal reading.
